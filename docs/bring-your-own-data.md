# Bring your own data

The workflow accepts your sources and explicit labels or reviewed model proposals. It does not assume a particular setting, game system, or speaker numbering scheme. Use a new workspace outside every Git checkout so generated source snapshots, reviews, and model weights cannot enter this repository accidentally.

## Configuration

Save a YAML file in your private working directory. Paths resolve relative to that file. Model files and the optional training Python executable may be absolute paths.

```yaml
version: 1
workspace: run-a
model: /path/to/local/qwen
runtime: /path/to/llama.cpp
base_gguf: /path/to/local/base.gguf
python: /path/to/training-environment/bin/python

# Optional task context. It is included in the recorded prompt and review identity.
system_context: "Preserve participant choices and use supplied evidence."
allow_model_reviews: false
allow_synthetic: false

conversations:
  - path: conversations/train.json
    format: turns-json
    group: conversation-family-a
    source_identity: recording-a
    split: train
    speakers:
      speaker-a: facilitator
      speaker-b: player
  - path: conversations/validation.json
    format: turns-json
    group: conversation-family-b
    source_identity: recording-b
    split: validation
    speakers:
      speaker-c: facilitator
      speaker-d: player

rule_documents:
  - id: local-rules
    path: references/rules.txt
    format: text
rule_excerpts:
  - id: movement-cost
    document: local-rules
    quote: "An exact excerpt from your local reference goes here."
rule_questions: questions.json

# Optional declared calculation interfaces. Inputs must be supplied explicitly
# in each question, and generated calls must match them. No tool is executed here.
tools: []

tasks:
  classifier:
    window_turns: 8
    context_turns: 8
    sequence_len: 4096
    epochs: 2
  rules:
    sequence_len: 4096
    epochs: 2
  storyteller:
    context_turns: 64
    sequence_len: 4096
    epochs: 2

serving:
  port: 8092
  layout: split
  tensor_split: "1,1"
  context: 16384
  slots: 1

evaluation:
  reload_cases: 4
  max_tokens: 512
  seed: 42
  startup_timeout: 240
```

Replace the placeholder excerpt with text present in your reference. Include independent `train` and `validation` sources for all three tasks; add `test` sources for final assessment. A task can specify a `recipe` path or a `max_steps` limit. Classifier/rules default to the general recipe; the storyteller uses the response-specific recipe. The one-step limit generated by `init-demo` is for integration testing only.

The recipe's `sequence_len` is a **training-example limit**. Serving `context` is a **per-request inference limit**. Increasing either can exceed available memory. Multiple serving slots multiply context allocation, and different task adapters may queue rather than batch.

## Conversations and speaker mappings

For `turns-json`, the input is an object with a `turns` array:

```json
{"turns": [
  {"speaker": "speaker-b", "text": "The participant's original contribution."},
  {"speaker": "speaker-a", "text": "The facilitator's original response."}
]}
```

The displayed snippets describe the format; supply actual original text in local files. Optional timestamps and alignment metadata are retained in source provenance, outside the model prompt; dialogue is not duplicated as word-by-word timing records. Logical turn numbers follow source order and begin at one. `speaker-text` accepts the formatter's `SPEAKER_00: ...` convention; WhisperX JSON preserves word timing and speaker boundaries. Set mappings for the speaker labels actually present in each source: `facilitator`, `player`, or `observer`.

Unknown speakers remain unknown. A narrator example requires a mapped facilitator response following a player's contribution; uncertain speaker context is not quietly turned into training supervision. Consecutive facilitator fragments form one response. The complete preceding player stimulus and preceding facilitator exchange remain protected during context fitting.

Classifier examples contain `target_turns`, preceding `context_only`, and optional supplied `prior_events`. If you supply prior events on a conversation entry, each needs `id`, `turn`, and `kind`; only events preceding the current target window are supplied. Resolution and correction links cannot name events absent from that context. The builder does not infer authoritative prior state from its own generated labels.

## Rule references and questions

Text references require no additional tools. For PDFs, set `format: pdf` and install Poppler's `pdftotext`. Extraction uses reading order. An excerpt may include a one-based PDF `page`; its `quote` must match that page, allowing whitespace normalization. Original document and extracted excerpt hashes are retained.

Supply a JSON question catalog:

```json
[
  {
    "id": "question-a",
    "group": "question-family-a",
    "split": "train",
    "question": "Your question about the supplied rule.",
    "references": ["movement-cost"]
  },
  {
    "id": "question-b",
    "group": "question-family-b",
    "split": "validation",
    "question": "An independently held-out question.",
    "references": ["movement-cost"]
  }
]
```

An item may include a `target` answer in the contract described below. Otherwise, annotate it manually or request a local model proposal. Use different groups for independent question families; paraphrases of one question stay together. The example deliberately reuses a reference: that evaluates questions over known supplied material, **not generalization to unseen rule documents**. The preparation report counts reference excerpts shared across splits. Choose disjoint references yourself when the intended study requires that stronger separation.

## Candidate preparation and review

```sh
ttrpg-pipeline candidates /path/to/private/experiment.yaml
```

Open `run-a/review.html`. It provides numbered navigation, source inputs, candidate IDs, targets, and review status. `review.json` is the editable label worksheet. Classifier targets initially have no annotation; storyteller targets preserve the actual response; rule answers use supplied labels or remain empty.

Edit only `target` fields for classifier/rules labels. Do not rewrite input context or narrator wording. Source changes need a fresh workspace and new reviews. The same guards apply when labels come from an annotation service.

### Label contracts

- **Classifier:** `events` and `uncertainties`. Events identify `kind`, `entity`, `attribute`, `value`, `delta`, `stage`, `visibility`, `evidence`, `resolves`, and `supersedes`. `evidence` contains exact `turn`/`quote` pairs and must cite the target window. Resource changes require established outcomes; an action is not itself a completed effect. Claims retain reported status. Source membership does not prove that a proposed label is semantically supported.
- **Rules:** `answer`, `citations` (`id` and exact `quote`), `calculation`, and `missing_information`. An assertion needs a supplied citation or an explicit information gap. `calculation` is null unless a declared tool can be called using explicit supplied inputs.
- **Storyteller:** `narration`. Preserve the complete original response. Review whether it actually responds to the preceding players, respects agency, and is suitable supervision; a transcript continuation is not automatically a good example.

`contracts.py` supplies the exact Pydantic models and runtime JSON schemas. Training serialization and constrained generation use the same field ordering and explicit nullable fields.

For a calculation, declare its name and JSON Schema under `tools`. A question may provide `tool_inputs: {tool-name: {...}}`; a target calculation uses `{"tool": "tool-name", "arguments": {...}}`. Arguments must validate against the declaration and equal the supplied inputs. This trains routing and abstention; the toolkit does not execute arbitrary functions or contain a hidden game-specific calculator.

### Optional local label proposals

Start an untuned local base server, or use an existing adapter server with its actual routing file. With a base-only server, routing is `{"adapters": [], "tasks": {}}`.

```sh
ttrpg-pipeline annotate /path/to/private/experiment.yaml \
  --task classifier --routing /path/to/private/server/routing.json \
  --url http://127.0.0.1:8091/v1 --limit 10

ttrpg-pipeline annotate /path/to/private/experiment.yaml \
  --task rules --routing /path/to/private/server/routing.json
```

The tool verifies the server's adapter inventory and sets every adapter scale to zero. Only loopback URLs are accepted; tunnel a remote GPU server locally. Outputs and failures are recorded under `annotations/`, and valid proposals are marked `model-proposed`. They remain **pending review**. Exact quotes and schema validation do not make model-generated labels correct or independent ground truth.

### Record a decision

After inspecting or correcting a target:

```sh
ttrpg-pipeline review /path/to/private/experiment.yaml \
  --id CASE_ID --decision keep --origin human --reviewer operator \
  --reason "Checked the cited turns and the distinction between a request and an outcome."
```

For storyteller targets, add `--response-complete` after checking the response boundary and relationship to the player stimulus. Use `--decision reject` for unsuitable examples. `--all --task TASK` records a batch decision when the whole selected batch has actually been reviewed; it is not an automatic quality check.

Record the actual reviewer origin. `model` is available for model review, with `allow_model_reviews: true` required before preparation. Such rows remain model-reviewed. `synthetic` is reserved for original fixtures and requires `allow_synthetic: true`. Review history retains previous and updated worksheets. A target change after approval requires another recorded review.

## Prepare and execute

```sh
ttrpg-pipeline prepare /path/to/private/experiment.yaml
ttrpg-pipeline plan /path/to/private/experiment.yaml
ttrpg-pipeline run /path/to/private/experiment.yaml
```

Preparation requires reviewed training and validation examples for all three tasks. It checks split isolation across tasks, writes three separate immutable snapshots, and records skipped/oversized cases. Structured tasks may have identical labels for different independent inputs; the narrative pipeline also rejects repeated responses across splits.

`plan` validates inputs and displays the training commands without starting GPU work. It fingerprints source/configuration files, model weight shards, and available inference runtime artifacts. Large-file hashes are cached against size and modification/change times. `run` performs training → strict reload/loss check → conversion for each task, then paired generation over validation and test examples.

The public runner does not stop other services. It refuses training when the two GPUs are occupied. Use `--through train`, `--through reload`, or `--through convert` to stop after a specific stage across all tasks. Run without that flag to complete evaluation.

## Resume and inspect

Run the same command again after interruption. Completed stages are skipped only after their artifact hashes pass. Failed stages keep their logs and retry in a new attempt directory. Training uses the latest saved optimizer checkpoint when one exists; without a checkpoint, that incomplete training stage starts again. A workspace lock prevents concurrent runners.

Changing sources, labels, settings, code, model files, or runtime identities requires a new workspace. This preserves the meaning of a completed experiment rather than silently mixing revisions. A changed virtual-environment executable or dependency set also needs deliberate assessment; each training run records installed package versions.

Important outputs beneath the workspace:

```text
review.json / review.html       editable labels and navigable source review
review-history/                previous and updated review snapshots
annotations/                   local label proposals and failures
datasets/{task}/               source rows, token rows, masks, and hashes
runs/{task}/                   recipe, attempts, checkpoints, portable adapter
attempts/{task}-{stage}/        strict reload and conversion reports / logs
pipeline.json                  stage state, commands, artifacts, failures
deployment.json                selected verified adapter paths
evaluations/{attempt}/          temporary server and paired model reports
serving/{run}/                  foreground server's routing and run metadata
```

A truncated generation is recorded as a model failure and never counts as a control pass. It does not abort the remaining cases: an evaluation stage can finish with failed responses and pending semantic review. Choose an output budget appropriate for the structured replies you expect; short budgets can cut off multi-event extractions.

The evaluation server is stopped after the comparison, including on infrastructure failures. Run `serve` to start a foreground application endpoint. It uses only adapters that passed the recorded training, reload, and conversion checks, and defaults to one request slot across two GPUs.

Open the validation A/B page before its separate identity key. Treat test results as final assessment: if they influence another model or prompt choice, reserve new cases before making an unseen-data claim. Control failures, exact label agreement, loss, latency, and semantic judgments answer different questions. The reference response is not the only acceptable continuation.
